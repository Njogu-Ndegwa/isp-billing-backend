Confirmed compatibility gaps:

- `app/services/ap_adapters.py:49` and `:133`: login only encodes raw MD5/Base64 and supplies a `password` cookie. The device's served `login.js` instead gets a challenge from `/goform/getstok` and computes `MD5(Base64(password) + random)`. The working browser session uses `ecos_pw`. No challenge, digest, cookie value or password is included in this report.
- `app/services/ap_adapters.py:218` and `:330`: generic and F3 adapters request `/goform/getSysStatusInfo` and `/goform/GetRouterStatus`. The authenticated device returns HTTP 200 HTML saying each form is not defined. Its working endpoint is `/goform/getStatus?modules=internetStatus,systemInfo,wifiRelay`, returning nested JSON. Its firmware key is `systemInfo.softVersion`; operating mode is `wifiRelay.wifiRelayType`, where `disabled` means normal router mode. The physical model was not independently established.
- `app/services/ap_control.py:369` / `:380` and `app/api/customer_cpe_routes.py:164`: unsupported status is classified as a failed login and increments the credential counter. One status call left the count at 1 despite a verified working password in the device UI. Repeated checks risk an incorrect credential lockout; further attempts were stopped.

Diagnostic read-only follow-up through the MikroTik at 19:46:27 fetched the challenge successfully. A challenge-encoded login at 19:46:29 returned 302, but a subsequent status request without the device's session cookie also returned 302. This is not an authenticated-status pass; it demonstrates that implementing the encoding alone is insufficient. At 19:46:26 the target PPPoE session was still active at the same address, uptime 3m13s, identity matched. The browser's authenticated LAN request returned the correct status JSON.
