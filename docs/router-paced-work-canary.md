# Paced router work canary

Status: rejected for rollout. The canary target was to avoid sampled 100% CPU during normal operations, with realistic small payment and expiry cohorts. A serving RB951 reached 100% in four of 185 samples (53.049% mean total CPU); its paced sources were rolled back. Earlier strict 1–2 percentage point peak acceptance was also not met. Pacing remains opt-in; unchanged defaults do not authorize a fleet rollout. See the [runtime architecture review](router-runtime-architecture-review.md) for the next mechanism without RADIUS.

`render_expiry_reaper_script(removal_limit=5)` considers at most five customer identities per invocation, one identity at a time. It yields for 1.4 seconds before each identity and rechecks CPU immediately before removal. At 85% CPU it starts no further removal. It also re-reads live user/binding expiry tags, protecting a renewal that arrived after the server response. The single-customer removal has no artificial sleeps after access is disabled. Unprocessed EXP records remain discoverable. Disable-before-kick, live authorization proof, retry after deletion failure and acknowledgement retention are preserved. Acknowledgement uploads remain capped at 40, independently of the number removed per pass.

`render_checkin_applier_source(mutation_limit=2)` and the canonical check-in installer validate the entire server frame before applying at most two lines per invocation. They check the same CPU threshold and yield between configuration stages. Unapplied entries remain absent from the next census, so server reconciliation retries them. These controls can increase backlog completion latency; a cap must not be described as instant processing of an entire server response.

These are cooperative limits, not a RouterOS CPU quota. An individual native command cannot be preempted by the renderer, and CPU sampling is delayed. A busy forwarding workload can exhaust the router independently. Real hardware measurements, realistic active-session disconnects and post-install reporting checks determine canary acceptance.

Check-in can use HTTP inside the existing encrypted management tunnel. The tunnel listener must first permit only the check-in path for explicitly selected canary source addresses, forwarding to the existing authenticated backend. Validate the Caddy configuration before a hot reload, retain the previous configuration, and keep unrelated source addresses denied. No native-census backend change is necessary for compatible check-in transport.

Do not replace public HTTPS for all routers through the global endpoint setting. Render only the selected canary router with the tunnel URL, preserve its original source and scheduler settings, and verify real check-ins from the running application worker before removing a timed rollback. Loss of the management tunnel also interrupts this check-in transport; this tradeoff must remain visible in rollout assessment.

RouterOS 6 and a fleet rollout remain outside the validated canary scope.

Final loaded spare tests used 20 active sessions, 32 configured accounts and 200 aggregate UDP packets/second with 1024-byte payloads plus equal echo return traffic, through VXLAN inside WireGuard. Five expiries peaked at 76% total CPU, and a 20-entry expiry backlog with five processed peaked at 75%. Means were 47.8% and 45.467%; runs took approximately 10 seconds. A renewal injected after the server response preserved all 20 session IDs and acknowledged no removal. A CPU-deferral branch injected a reading of 90%; that branch test did not create an actual 90% workload. Loaded payment frames of one/two/five with the two-line cap created one/two/two users and peaked at 41%/62%/67%. These are total CPU results with drifting traffic baselines, not incremental script CPU measurements.

The final source passed 262 focused tests. All spare sources, schedule settings and pool settings were independently restored; synthetic accounts, sessions and network objects were absent. The rejected serving-router canary and its restricted proxy route were reverted. No backend application deployment or fleet rollout occurred.
